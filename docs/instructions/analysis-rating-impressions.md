### 1-1. 현재 구현

**보정 별점과 별점 점수** — `lib/engine.js:325~335`

```js
// 보정 별점: 리뷰가 적을수록 동네 평균 쪽으로 당긴다. 리뷰 수 데이터가 없으면 원래 별점.
const RATING_PRIOR_REVIEWS = 10;
function adjustedRating(s, avg) {
  const n = s.review_count;
  if (s.rating == null || n === 0) return avg;
  if (n == null) return s.rating;
  return (n * s.rating + RATING_PRIOR_REVIEWS * avg) / (n + RATING_PRIOR_REVIEWS);
}
function ratingScore(s, avg) {
  return clamp((adjustedRating(s, avg) - 3.5) / 1.5);
}
```
- 별점 점수는 `ratingScore × 20`이다. 쓰이는 곳은 세 군데: `lib/engine.js:872`(좁히기 질문 후보 사전 점수), `:907`(맞음 판단 전 사전 점수), `:972`(최종 점수 = 조건 일치 + 가격×30 + **별점×20**).
- 보정 별점 3.5 이하는 0점, 5.0은 20점으로, 선형으로 바뀐다.

**지역평균** — `lib/engine.js:296~297`

### 1-4. 고쳐야 할 점 (제안만, 구현하지 않음)

1. **snapshot에 `review_count` 추가 (필수)**
   - `supabase/migrations`에 새 마이그레이션을 만들어 `recommendation_catalog.snapshot()`의 stores `jsonb_build_object`에 `'review_count', s.review_count`를 넣는다.

   - DB를 바꾸는 작업이라 팀 합의 후 적용해야 한다.
2. **null 처리 결정**: 요청 문구("0이거나 빈 별점")를 그대로 따르면 지금 코드가 맞다. 다만 데이터가 빠졌을 때 보정이 조용히 꺼지지 않게 하려면, `n == null`도 지역평균(또는 `n = 0` 취급)으로 바꾸는 걸 제안한다. 바꾸면 1번이 적용되기 전에는 모든 가게 별점이 지역평균이 되어 별점 변별력이 0이 되니, 1번을 먼저 하는 게 좋다.

4. **테스트 보강**: 지금 테스트(`test/recommend.test.js`의 `[P0-4] 보정 별점·신규 가게·영업 여부`)는 review_count가 있는 경우만 본다. 1-3의 B 시나리오(review_count 필드 없음)를 기대 동작에 맞춰 추가한다.

## 요청사항 2. 노출 횟수 DB 저장

### 2-1. 현재 구현

**저장소: 서버 메모리** — `lib/engine.js:111~119`
```js
// ---------- 노출 횟수 (가게별, 매일 0시 초기화) ----------
// ponytail: 서버 메모리라 재시작/서버리스 인스턴스마다 초기화됨. 유지가 필요하면 Supabase 테이블로.
const exposure = { day: '', counts: {} };
...
function expo(id) {
  const day = dateFormat.format();
  if (exposure.day !== day) { exposure.day = day; exposure.counts = {}; }
  return (storesById.get(id)?.exposure_count ?? 0) + (exposure.counts[id] ?? 0);
}
```
- 읽기(`expo`)는 **DB 값(`exposure_count` = DB `impressions`) + 메모리 값**을 더해서 쓴다.
- 매일 0시(서울 시간)에 메모리 값을 초기화하는 코드가 **있다** (이번 요청에서는 필요 없음).

**기록: 추천을 보여줄 때 메모리 +1** — `lib/engine.js:751~758`
```js
function rememberCards(state, cards, displayed = cards) {
  for (const { storeId } of cards) {
    if (!state.exposed.includes(storeId)) {
      expo(storeId);
      exposure.counts[storeId] = (exposure.counts[storeId] ?? 0) + 1;
      state.exposed.push(storeId);
    }
    ...
```
- DB에 쓰는 호출이 없다. `lib/`, `api/` 전체에서 Supabase 호출은 snapshot 읽기(`api/recommend.js:17`) 하나뿐이다.
- `supabase/migrations`에도 impressions를 +1 하는 RPC가 **없다**. `impressions`는 테이블 정의(`20261116123136…sql:13`)와 snapshot 출력(`20261121011721…sql:26, 36`)에만 나온다.
- **같은 대화에서 한 가게는 1번만** 센다(`state.exposed`). "처음부터"를 하면 `fresh()`(`:140`, `:1176~1178`)가 `exposed`를 비워서 다시 센다.
- **TOP3만 세는 게 아니다.** 화면에 보여준 카드를 모두 센다.
  - `rememberCards` 호출 위치는 `:796`(여러 음식 조합), `:853`, `:1056`(일반 결과)이다.
  - "다른 데는?"으로 본 다음 3곳도 세고, "나머지 N곳도 보여줘"로 한 번에 최대 36곳을 보여주면 그 36곳도 모두 센다.

**TOP3 고르기: 1등과 5점 이내는 덜 노출된 순** — `lib/engine.js:1006~1009`
```js
scored.sort((a, b) => b.score - a.score);
const [first, ...rest] = scored;
const peers = rest.filter(r => first.score - r.score <= 5).sort((a, b) => expo(a.s.id) - expo(b.s.id) || Math.random() - 0.5);
const priority = [first, ...peers, ...rest.filter(row => !peers.includes(row))];
```
- 1등은 고정이고, 1등과 5점 이내인 가게들을 노출 값이 적은 순으로 놓는다. **노출 값이 같으면 `Math.random`으로 섞는다.**
- 이 뒤에 브랜드 중복 제거(`diversify`)를 하고 3곳을 자른 다음, 화면에는 점수순으로 다시 정렬한다(`:1018 pick.sort`).
- 사전 점수 정렬(`:873`, `:912`)에서도 동점이면 `expo`가 적은 순이다.

**카탈로그 캐시와 메모리 수명** — `api/recommend.js:8~9, 14~30`
- `CATALOG_TTL_MS = 10분`이다. 커밋 `34ea109`에서 2분 → 10분으로 바꿨다.
- 캐시가 만료되면 **`createEngine(snapshot)`을 새로 만든다.** 이때 `exposure` 객체도 새로 만들어지므로, **메모리 노출 값은 최대 10분마다 사라진다.** 서버 재시작이나 다른 서버리스 인스턴스에서도 마찬가지다.
- DB 값은 snapshot을 받을 때만 읽으므로, DB에 +1을 하더라도 **최대 10분 늦게** 반영된다.

- 무작위를 없애도 똑같이 돌아가므로, **순서가 바뀌는 건 노출 값 덕분**이다.
- 무작위는 노출 값이 같은 가게끼리(예: 1회차의 0인 가게들) 어느 쪽을 먼저 보여줄지만 바꾼다. 그래서 무작위를 켜면 1회차의 2·3등이 실행마다 달라진다.

**DB 값 변화**: 시나리오 실행 전후 모두 DB impressions가 0이 아닌 가게는 **0곳**이다. 코드에 DB 쓰기가 없으므로 실제 DB에서도 바뀌지 않는다(이번 분석은 DB에 쓰지 않았다).

### 2-4. 고쳐야 할 점 (제안만, 구현하지 않음)

1. **+1 RPC 추가 (DB)**
   - 예: `public.seoul_record_impressions(store_ids text[])` → `update recommendation_catalog.stores set impressions = impressions + 1 where store_id = any(store_ids)`
   - `security definer`로 만들고, anon에는 실행 권한만 준다.
   - 한 번에 받는 개수에 상한(예: 3~5개)을 두고, 존재하는 store_id만 갱신한다.
   - DB 변경이라 팀 합의 후 마이그레이션으로 적용한다.
2. **호출 위치**: 엔진은 DB를 모르게 두고, `api/recommend.js`에서 `handle()` 결과의 TOP3 `storeId`를 이 RPC로 보낸다.
   - 요청대로 **확정된 TOP3만** 보내려면 `reply.cards.slice(0, 3)`만 보낸다. 다른 데는?/나머지 N곳을 셀지는 정해야 한다.
   - 응답 시간에 영향이 없게 응답 뒤에 보내거나 실패를 무시한다. 같은 대화 중복 방지는 지금의 `state.exposed` 규칙을 재사용할 수 있다.
3. **동점 비교를 DB 값으로**
   - `expo()`에서 메모리 합산(`exposure.counts`)을 빼고 DB 값만 읽는다.
   - 다만 snapshot 캐시(10분) 때문에 DB +1이 늦게 보인다. 둘 중 하나를 택한다.
     - (a) 캐시가 갱신되기 전까지는 "DB 값 + 이 인스턴스가 보낸 +1"을 임시로 더한다(지금 구조와 비슷).
     - (b) TOP3 결정 직전에 후보 가게들의 impressions만 가볍게 다시 읽는 RPC를 따로 둔다.
4. **불필요한 코드 정리**: DB로 옮기면 메모리 `exposure` 객체와 매일 초기화(`expo`의 날짜 비교)는 제거하거나 (3-a)의 임시 보정용으로만 남긴다.
5. **무작위**: 노출 값이 같을 때의 `Math.random`은 공정성 면에서 문제는 없다. 다만 테스트와 시연에서 결과가 매번 달라지니, 동점이면 store_id 순 같은 결정적 기준을 고려할 수 있다.
6. **테스트**: RPC 호출부를 가짜 함수로 바꿔, "TOP3 store_id만 1번씩 전달되는지"와 "같은 대화에서는 중복 전달이 없는지"를 확인하는 테스트를 추가한다.
