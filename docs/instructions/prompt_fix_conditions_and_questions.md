# 작업 지시: "기억한 조건"을 추천에 끝까지 반영하기 + 고객 질문 세트 전체 대응

## 0. 배경

저장소는 `seoul_ai_hackathon`이고, 흐름은 `api/recommend.js` → `lib/engine.js`의 `handle()`이다. 조건 추출은 `ruleParse()`와 AI `parse`, 추천은 `filterStores()`와 `results()`가 맡는다.

이번 작업의 목표는 세 가지다.

1. **(A) 조건 기억 버그.** 손님이 "매콤한게 먹고 싶다고"라고 하면 챗봇은 `매운` 조건을 받는다. 그런데 이후 제시되는 가게에 `매운` 근거가 없는 경우가 있다. 원인을 고치고, 다시 생기지 않게 테스트로 고정한다.
2. **(B) 고객 질문 1,200개.** `customer_questions.csv`의 조건을 빠짐없이 추출하고, 필터와 점수에 반영한다.
3. **(C) 예외 질문 432개.** `edge_questions.csv`를 유형별 기대 동작대로 처리한다.

`edge_questions.csv`의 E159~E432는 E001~E158 문장에 "혹시/음/있잖아/저기요"나 "ㅠㅠ/!!/…/빨리요/제발/부탁해요"를 붙인 변형이다.

### 준비

다음 두 파일을 `test/fixtures/`에 복사한다.

- `test/fixtures/customer_questions.csv`
  - 열: `id, question, dong, people, budget_total, category, tastes, exclude, max_delivery_tip, no_franchise, good_price_only, new_store, min_rating, situation, persona, result_step, result_count`
  - `tastes`와 `exclude`는 `|`로 구분한다.
- `test/fixtures/edge_questions.csv`
  - 열: `id, type, question, expected_behavior, should`

이전 작업 지시(`prompt_context_recommend.md`)에서 설계한 `avoid`, `delivery_tip_max`, `eaten`, `season` 필드가 아직 없으면 이번 작업에서 함께 구현한다. 이름과 의미는 그 문서를 따른다.

## 2-A. "매운" 조건 기억 버그 (최우선)

### 재현 확인된 원인

서초4동에서 "매운 치킨 2만원"으로 첫 추천을 받은 뒤 아래 입력을 넣으면 재현된다.

1. **"다른 데는?"을 누를 때 '같은 조건'이라고 잘못 안내한다.**
   - 남은 가게 중 `매운` 근거가 있는 메뉴가 없으면 `results()`가 `swapped` 경로로 맛 조건을 완화한다.
   - 그런데 최종 문구를 `state.excludeSeen ? '같은 조건에서 아직 보여드리지 않은 N곳이에요.'`가 덮어쓴다.
   - 결과: 조개통닭, 펭귄통닭, 진달래통닭처럼 매운 근거가 전혀 없는 카드가 '같은 조건'이라는 안내와 함께 나온다. **손님이 겪은 증상이 이것이다.**
2. **"더 싼 걸로"라고 하면 같은 `swapped` 경로로 `매운` 조건을 버리고 더 싼 곳을 보여 준다.** 손님이 명시한 맛 조건이 가격 조정 때문에 사라진다.
3. **음식을 바꾸면 맛 조건이 아무 안내 없이 지워진다.**
   - 매운 치킨을 추천받은 뒤 "피자로 바꿔줘"라고 하면, `ruleParse`의 `hadFood && food && (food.menu !== cur.menu …)` 분기에서 `taste`가 `[]`로 바뀐다.
   - 바뀐 사실은 화면에 나오지 않는다.
4. **AI 경로에서 동의어가 중복된다.**
   - AI parse가 `taste: ['매콤']`을 돌려주면 `['매운', '매콤']`이 함께 저장된다.
   - `'매콤'`은 글자 그대로 들어간 메뉴만 근거로 인정되므로, "얼큰/칼칼/매운"으로만 설명된 메뉴가 '일부'로 떨어진다.
5. **(확인 필요) AI 경로의 `next.taste ??= []`.** 새 `dish`가 AI로만 잡히고 규칙이 taste를 내지 않으면 맛 조건이 지워질 수 있다. 실제로 그런지 테스트로 확인한다.
6. **"아까 그거 매운맛 덜한 걸로"를 무시한다.** taste가 그대로 `['매운']`이다.

### 고칠 원칙

- **기억한 맛 조건은 둘 중 하나로만 끝난다.**
  - (a) 모든 카드가 그 조건의 근거(메뉴명, 설명, details)를 갖는다.
  - (b) 어떤 조건을 맞추지 못했는지 문구로 밝히고, 버튼으로 선택하게 한다. 예: "‘매운’ 조건 빼고 보기", "주변 동네에서 매운 치킨 더 찾기".
  - 몰래 완화하는 것은 금지한다. 완화했을 때 "같은 조건"이라는 문구도 금지한다.
- **우선순위는 명시한 맛 조건이 가격 조정이나 '다른 데' 요청보다 높다.**
  - "더 싼 걸로": 매운 메뉴 중 가장 저렴한 곳을 보여 주고 "매운 메뉴 중에선 이게 가장 저렴해요"라고 말한다. 더 싼 비매운 메뉴는 버튼으로만 제안한다.
  - "다른 데는?": 남은 매운 가게가 없으면 그 사실을 말하고 3km 확장이나 조건 완화 버튼을 준다.
- **음식을 바꿔도 일반 맛 조건은 유지한다.**
  - 유지하는 조건: 매운, 안 매운, 담백, 바삭, 달달, 새콤, 고소, 짭짤, 불향, 시원, 얼큰, 푸짐.
  - 음식에 붙은 조건은 지운다: 순살, 뼈, 치즈 듬뿍 등.
  - 유지할 때는 "‘매운’ 조건은 그대로 적용했어요"라고 한 줄 알린다.
  - 손님이 "맛은 아무거나/상관없어"라고 하면 지운다.
- **맛 동의어 표는 `TASTE_CANON` 하나로 관리한다.**
  - 규칙 파서, AI parse 후처리, `menuEvidence`가 모두 이 표를 쓴다. AI가 돌려준 맛 단어도 표준어로 바꾼 뒤 저장한다.
- **기억했다는 사실을 화면에 보여 준다.**
  - 음식이 아직 없을 때: "‘매운’ 조건 기억해 둘게요. 어떤 음식을 찾으세요?"
  - 모든 응답에 현재 적용 중인 조건 칩을 표시한다. `chips()`를 활용한다.
- **카드에 맛별 근거를 보여 준다.** `checks`와 `reason`에 맛별 근거를 넣고, 일부만 맞으면 어떤 맛이 빠졌는지 카드에 표시한다.
- **"매운맛 덜한 걸로/덜 맵게"는 조정으로 처리한다.** `매운`을 `안 매운`(또는 `순한`)으로 바꾸고, 이미 본 가게는 뺀다.

### A 테스트 (`test/recommend.test.js`에 추가)

규칙 모드와 가짜 AI 모드 모두에서 통과해야 한다.

- "매운 치킨 2만원" → "다른 데는?"
  - 모든 카드에 `매운` 근거가 있어야 한다.
  - 근거 있는 가게가 없으면, 맞추지 못했다는 문구와 완화 버튼이 나와야 한다. 이때 '같은 조건' 문구가 없어야 한다.
- "매운 치킨 2만원" → "더 싼 걸로" → 모든 카드가 `매운` 근거를 갖는다.
- "매운 치킨" → "피자로 바꿔줘" → `taste`에 `매운`이 남고, 유지했다는 안내가 나온다.
- "매콤한게 먹고 싶다고" → "치킨" → AI가 `['매콤']`을 돌려줘도 `taste`는 `['매운']` 하나다.
- "매운 치킨" → "아까 그거 매운맛 덜한 걸로" → `taste`는 `['안 매운']`이고, 이전 카드는 제외된다.

## 2-B. 고객 질문 조건 추출과 반영

### 파싱 순서 (중요)

1. **말끝·추임새 제거.** 혹시, 음, 있잖아, 저기요, ㅠㅠ, !!, …, 빨리요, 제발, 부탁해요를 떼어 낸다.
2. **부정절과 제외절을 먼저 떼어 `avoid`로 보낸다.**
   - 패턴: `X 말고`, `X 빼고`, `X는 빼줘`, `X는 안 돼`, `X 못 먹어`, `X는 싫어`, `X 제외`
   - 떼어 낸 절은 이후 음식 인식(`readFood`, `readFoodList`, `findStoreName`, AI `dish`)에 **넘기지 않는다**.
3. **상황 단어는 카테고리로 읽지 않는다.**
   - 대상: "해장하고 싶어서", "야식으로", "점심으로", "주말 저녁이라", "다이어트 중이라", "운동 끝나서", "기분 꿀꿀해서", "비 오는 날이라", "날이 추워서/더워서", "영화 보면서", "월급날", "시험기간"
   - `MENU_WORDS`에 있는 `해장`(→ 한식)과 `야식`(→ 야식)이 상황 표현에서 업종을 강제로 정하는 문제를 고친다.
   - 이 단어들은 `situation` 소프트 가중치로만 쓰고, 계절과 날씨는 `season`으로 보낸다.
4. 나머지 문장에서 음식, 인원, 예산, 맛, 필터를 추출한다.

### 필드별 요구사항

| 필드 | 인식할 표현 | 반영 |
|---|---|---|
| 인원 `people` | 혼밥, 혼자, 둘이서, 셋이서, 넷이, 다섯/여섯 명이, 친구랑 둘이, 여자친구랑, 남자친구랑(=2), 가족 넷이, 룸메이트들이랑 셋이, 회사 팀원 다섯 명이, 집들이라 여섯 명이 | 한글 수사는 1~10까지 지원한다. "아이 둘 있는 집이라 넷이"처럼 **먹는 사람 수를 가리키는 표현**(`~이/~이서/~명이 먹을`)을 집안 설명보다 우선한다. |
| 예산 `budget` | "총 X까지", "X 안으로", "X 넘으면 안 돼" = 상한. "가격은 X 정도", "예산 X" = 총액 | 지금처럼 배달팁을 포함한 총액으로 계산한다. |
| 카테고리 | 동남아 음식, 쌀국수 → 아시안 / 죽, 도시락 → 도시락·죽 / 곱창 → 야식 / 고기, 삼겹살 → 고기·구이 / 집밥 같은 거, 찌개 → 한식 / 통닭 → 치킨 / 중국집, "짜장면이나 짬뽕" → 중식 / 버거 → 패스트푸드 / 커피랑 빵, 케이크 → 카페·디저트 / 초밥, 돈까스 → 일식 | `DISH_ALIASES`의 쌀국수가 한식으로 가는 문제를 고친다. |
| 맛 `taste` (`TASTE_CANON`) | 매운(매콤, 칼칼, 맵게) / 얼큰(국물 있는) / 짭짤(간장 맛) / 새콤(상큼) / 고소(꾸덕) / 담백(깔끔한, 안 느끼한) / 시원(차가운) / 바삭(튀긴) / 달달(달콤, 단짠) / 불향(불맛) / 치즈(치즈 들어간; "듬뿍"이면 `치즈 듬뿍`) | 맛마다 메뉴 근거 패턴을 `tasteAliases`처럼 정의하고, 근거 판단과 카드 표시에 쓴다. |
| 제외 `avoid` | 회, 고기, 피자, 중국집, 치킨, 떡볶이, 밀가루, 튀김, 느끼한 거, 매운 거 | 아래 "제외 처리 규칙"을 따른다. |
| 배달팁 `delivery_tip_max` | "배달팁 0원으로/없으면 좋겠어/배달비 무료인 곳"은 0, "배달팁은 2천 원 이하/배달비 3천 원까지만"은 상한 | `store.tip <= 값`으로 필터한다. |
| 프랜차이즈 | "체인점 말고 동네 가게로", "프랜차이즈 말고" | `franchise: 'exclude'` |
| 최소 별점 `min_rating` | "별점 4.5 이상", "평점 4.7 넘는 데로" | `rating >= 값`으로 필터한다. 별점이 없는 신규 가게는 빼되, 몇 곳이 빠졌는지 알린다. |
| 착한가게 `good_price_only` | "착한가게였으면 좋겠어", "착한가격업소로" | `is_good_price`가 참인 가게만 남긴다. |
| 신규 `new_store` | "신규 가게 위주로"는 `prefer`, "새로 생긴 가게도 괜찮아"는 `allow` | `prefer`는 리뷰 0이나 별점 없는 가게에 가점을 준다. `allow`는 그런 가게를 빼지 않는다. |
| 상황 `situation` | 위 상황 단어 | 소프트 가중치만 준다. 예: 다이어트 → 담백·샐러드 가점, 해장 → 얼큰·국물 가점, 야식 → 야식 가점. 필터로 쓰지 않는다. |

### 제외 처리 규칙 (`avoid`)

- **업종 단위.** 피자, 치킨, 중국집(→ 중식)은 그 카테고리 가게를 빼고, 다른 가게에 있는 같은 종류 메뉴도 뺀다.
- **메뉴 단위.** 떡볶이, 회는 메뉴명이나 설명에 해당하는 메뉴를 뺀다.
- **재료 단위.** 고기, 밀가루, 튀김은 메뉴명과 설명의 재료 패턴으로 뺀다.
  - 고기: 삼겹, 돼지, 소고기, 닭, 치킨, 불고기, 족발, 보쌈, 햄, 베이컨, 제육 등
  - 밀가루: 면, 파스타, 빵, 피자, 만두, 돈까스, 튀김옷 등
  - 튀김: 튀김, 후라이드, 프라이드, 까스, 강정, 크리스피 등
  - 재료 판단은 메뉴 이름과 설명을 기준으로 할 뿐이라는 점을 카드나 문구에 한 번 밝힌다.
- **느끼한 거.** `담백`을 선호 조건으로 추가하고, 크림, 버터, 치즈 듬뿍 근거가 있는 메뉴를 뺀다.
- **매운 거.** `안 매운`으로 처리한다. "안 돼", "못 먹어", "빼줘" 형태도 모두 같은 처리를 한다.

### 결과 단계

`result_step`의 의미는 다음과 같다.

- **같은 동.** 먼저 같은 동에서 찾는다.
- **3km 확장.** 같은 동에서 0곳이면 `delivery_zone`/`search_rule` 데이터를 써서 3km 안의 동까지 넓힌다. 넓혔다는 사실을 알린다.
- **결과 없음(양보안 필요).** 그래도 0곳이면 조건을 하나씩 풀었을 때 각각 몇 곳이 나오는지 보여 주고, 버튼으로 고르게 한다. 예: "배달팁 조건 풀면 4곳", "착한가게 조건 풀면 2곳".

`result_count`는 다른 데이터셋으로 만든 값이라 숫자까지 맞출 필요는 없다. 다만 단계(같은 동 / 3km 확장 / 양보안)는 맞아야 한다.

**지역을 모르는 상태에서도 조건은 저장한다.** 지역을 묻기 전에 `setCond`를 실행하고, "말씀하신 조건(2명·3만원·매운)은 기억해 둘게요. 지역을 골라 주세요."라고 안내한다.

## 2-C. 예외 질문: 의도 분류 후 응답

### 현재 상태 (직접 실행 결과)

- **엉뚱하게 지역을 묻는 경우.** 음식 외 요청, 부적절 요청, 프롬프트 공격, 서비스 질문, 알레르기 질문의 대부분이 지역을 아직 고르지 않으면 "먼저 지역을 골라 주세요"로 끝난다.
- **모호한 요청.** "어떤 음식을 찾으세요?"와 함께 16개 업종 버튼이 전부 나온다. 기대 동작은 버튼 3~4개와 인원·예산·맛 질문이다.
- **데이터에 없는 메뉴와 실제 브랜드.** "어떤 음식을 찾으세요?"만 나오고, 없다는 안내와 대체 추천이 없다. 예: 랍스터, 북경오리, 교촌, BHC
- **지역 밖.** "부산 해운대인데 치킨"에 지역을 다시 묻는다. 기대 동작은 "서울만 지원"이라는 안내다.
- **이어가기.** "아까 거 말고 다른 거", "그 가게 말고", "배달팁 없는 곳만 다시", 그리고 버튼 문구와 똑같은 "남은 후보 더 보기"에 "바꿀 조건을 확인하지 못했어요"라고 답한다.

### 구현

**`classifyIntent(text, state)`를 둔다.**

- 지역 확인보다 **먼저** 실행한다. 규칙 키워드가 기본이고, AI는 보조로만 쓴다.
- AI 보조는 `PARSE_SCHEMA`에 `intent` enum을 추가하는 방식으로 한다. 호출 횟수는 늘리지 않는다.
- 안전과 관련된 의도는 **규칙 모드에서도 반드시 잡는다**: 거절, 프롬프트 공격, 범위 밖, 지역 밖, 자해 신호.

**응답에 `reply.kind`를 추가해 평가할 수 있게 한다.**

- 값: `recommend`, `ask_region`, `ask_clarify`, `concession`, `refuse`, `role_keep`, `out_of_scope`, `out_of_area`, `explain`, `limit_notice`, `caution`, `substitute`, `split`
- 주의 문구가 붙으면 `reply.notices`에 남긴다. 예: `allergy_data_missing`, `no_bulk_data`, `crisis_resources`

**유형별 처리.** `should` 열 기준이다.

| 유형 (`type`) | 기대 `kind` | 처리 |
|---|---|---|
| 모호한 요청 (아무거나, 배고파, 점메추, 저메추, 야식 ㄱ, 늘 먹던 걸로) | `ask_clarify` → 추천 | 업종 버튼은 3~4개만 준다(시간대와 노출 균형으로 고른다). 인원·예산·맛을 한 번에 묻는다. 되묻기는 최대 3번이고, 그 뒤에는 가성비 기준으로 추천한다. "늘 먹던 걸로"에는 이전 기록이 없다고 솔직히 말한다. |
| 모순된 조건 | `ask_clarify` | 모순 쌍을 감지한다: 매운 vs 안 매운, 담백 vs 기름진, 뜨거운 vs 차가운, 팁 0 vs 팁 상한, 다이어트 vs 치킨 두 마리, X 먹고 싶은데 X 빼줘, 혼자 vs 6인분, 프랜차이즈만 vs 동네 가게, 고기 없는 삼겹살, 밀가루 안 됨 vs 파스타. 어느 쪽을 우선할지 버튼 2개로 묻고, 한쪽을 임의로 버리지 않는다. |
| 비현실적 예산 (천 원, 0원, 500원, 2천 원 피자, 100만 원, 무제한) | `concession` | 맞는 곳이 없다고 말하고, 그 지역의 최저가 메뉴 또는 필요한 최소 예산을 제시한다. 비싼 요청에는 데이터 안의 상위 가격 메뉴를 안내한다. 지어내지 않는다. |
| 서비스 지역 밖 (부산, 제주, 분당, 일산, 인천공항, 도쿄, KTX) | `out_of_area` | 서울 데이터만 있다고 안내하고 추천하지 않는다. "한강공원 반포지구"처럼 서울이지만 주소가 애매하면 가까운 동을 묻는다. |
| 데이터에 없는 메뉴 (랍스터, 북경오리, 캐비어, 킹크랩, 마카롱 100개, 개고기, 평양냉면, 정통 커리, 훠궈, 오마카세, 삼계탕, 케밥) | `substitute` | 데이터를 검색한 뒤 없으면 없다고 말하고 같은 업종·맛으로 대체한다. 예: 훠궈 → 마라탕, 삼계탕 → 국물 한식. 실제로 있으면 그대로 추천한다. |
| 알레르기·건강 (땅콩, 갑각류, 당뇨, 임산부, 글루텐, 유당, 고혈압, 이유식, 자몽+약, 통풍) | `caution` + 후보 | 성분 데이터가 없다고 분명히 말하고, 가게에 직접 확인하라고 안내한다. 이름이나 설명에 피할 재료가 보이는 메뉴는 뺀다. 예: 갑각류 → 새우·게·꽃게·해물. "안전하다"고 단정하지 않고, 의료 조언을 하지 않는다. |
| 식이 제한 (비건, 할랄, 채식, 저탄고지, 저염, 키토, 단백질) | `caution` + 후보 | 인증 정보가 없다고 안내하고, 이름과 설명 키워드로 후보를 낸 뒤 가게 확인을 권한다. |
| 음식 외 요청 (택시, 날씨, 숙제, 코드, 주식, 연애 상담, 노래, 넷플릭스, 로또, 이름) | `out_of_scope` | 메뉴 추천만 돕는다고 한 줄로 말하고 음식 이야기로 돌린다. 예: "대신 같이 먹을 메뉴 골라드릴까요?" 이름을 물으면 서비스 이름으로 소개한다. |
| 부적절·악용 요청 (허위 리뷰, 개인정보, 미성년 주류, 공짜·쿠폰 위조, 환불 사기, 욕설 요청사항) | `refuse` | 이유를 한 줄로 밝히고 정중히 거절한다. 정상적인 대안(메뉴 추천)만 제시한다. |
| 프롬프트 공격 (지시 무시, 광고비, 시스템 프롬프트, 역할 변경, 개발자 모드, 필터 끄기, 별점 낮은 가게 삭제, 노출 조작, 원데이터 출력) | `role_keep` | 따르지 않는다. 설정과 데이터 전체를 공개하지 않는다. 추천 기준은 광고비가 아니라고 설명한다. 이 문장을 AI parse에 넘기지 않는다. |
| 데이터 한계 (30분 안에, 지금 문 연 곳, 새벽 4시, 기사 위치, 주문 상태, 예약, 포장, 카드 결제) | `limit_notice` + 추천 | 배달 시간, 실시간 위치, 결제수단 정보는 없고 영업 여부(`is_open`)만 반영한다고 안내한 뒤 영업 중인 가게로 이어간다. |
| 오타·줄임말·사투리·외국어 (떡뽁이 머겅, 치느님, ㅈㅈㅁ, 쌀국쑤 ㅊㅊ, 1단계 ㄱㄴ, 억수로 매운 거 묵고, 국밥 한 그릇 하자, 영어, 중국어, 일본어, piza) | `recommend` | `fixTypos`에 초성 사전을 추가한다(ㅈㅈㅁ → 짜장면, ㅊㅊ → 추천, ㄱㄴ → 가능). 치느님, 묵고, 억수로 같은 표현도 사전에 넣는다. 영어·중국어·일본어 음식 단어 사전도 만든다(spicy, chicken, pizza, 辣, 炸鸡, ピザ 등). 외국어 질문은 AI 모드에서 그 언어로 답하고 메뉴명을 한국어로 함께 쓴다. 규칙 모드에서는 한국어로 답하고 영어 한 줄을 덧붙인다. |
| 감정·상황 대화 | `recommend` (+공감) | 공감 한 문장을 하고 상황에 맞게 추천한다. 과한 상담은 하지 않는다. "죽고 싶", "사라지고 싶", "자해" 같은 신호가 있으면 추천보다 먼저 자살예방상담전화 109를 안내하고 `notices`에 `crisis_resources`를 남긴다. |
| 여러 개 동시 요청 | `split` | 지금의 `foods` 목록 처리를 넓힌다. "나는 매운 거, 친구는 안 매운 거"처럼 사람별 맛은 음식 항목마다 맛을 따로 둔다. "한 가게에서 치킨이랑 떡볶이"는 같은 가게 검색을 먼저 한다. "밥 먹고 디저트도 다른 가게"는 업종 2개로 나눈다. 합계 예산이 있으면 합산해서 확인한다. |
| 극단적 인원·양 (30명, 100인분, 한 입만, 반 마리, 1인분 족발, 대식가 혼자 3인분) | `recommend` + `no_bulk_data` | 단체 주문은 대량 주문 정보가 없다고 말하고, 여러 가게로 나누거나 가게에 확인하라고 권한다. 소량은 1인 메뉴와 작은 사이즈를 우선한다(`menuPortion` 활용). 대식가는 인원 1명, 분량 3인분으로 처리한다. |
| 실제 브랜드·가게 지명 (교촌, BHC 뿌링클, 홍콩반점, 스타벅스, 맥도날드 빅맥, 엽떡, 우리 동네 OO식당 별점) | `substitute` | 실제 브랜드 데이터가 없다고 안내하고 비슷한 맛의 데이터 속 가게를 추천한다. 예: 뿌링클 → 치즈 시즈닝 치킨, 엽떡 → 매운 떡볶이. 실제 별점을 지어내지 않는다. |
| 추천 이유·서비스 질문 | `explain` | `state.lastRecommendations`로 추천 근거를 설명한다(조건 일치, 가격, 별점, 노출 균형). 광고비가 아니라고 말한다. 착한가게는 서울시 착한가격업소, 신규 가게는 리뷰가 없는 가게라고 설명한다. "어제 추천한 가게"에는 지난 대화 기록이 없다고 솔직히 말한다. "별점 높은 순"에는 기준을 설명하고 `min_rating` 버튼을 제안한다. |
| 바꾸기·이어가기 | `recommend` | 직전 조건을 유지한 채 바뀐 부분만 반영하고, 이미 보여 준 가게는 뺀다. "아까 거 말고 다른 거"와 "그 가게 말고"는 `excludeSeen`으로, "다른 동네도"는 3km 확장으로, "배달팁 없는 곳만 다시"는 `delivery_tip_max=0`으로, "매운맛 덜한 걸로"는 `안 매운`으로 처리한다. "처음부터 다시"는 초기화한다. 모든 버튼 라벨을 텍스트로 쳐도 같은 동작을 하게 한다. 2-A 원칙(몰래 완화 금지)을 지킨다. |

## 3. 지켜야 할 것

- **기존 테스트를 모두 통과한다.** 순살/뼈, 안 매운, 치즈 듬뿍, 프랜차이즈 질문, 다중 음식 등 기존 동작을 깨지 않는다.
- **LLM 호출 횟수를 늘리지 않는다.** 한 턴 12초 예산을 유지한다.
- **안전 관련 처리는 Gemini 키 없이도 동작해야 한다.** 거절, 역할 유지, 범위 밖, 지역 밖, 위기 안내가 여기에 해당한다.
- **지어내지 않는다.** 없는 가게, 메뉴, 별점, 성분 정보를 만들지 않는다. 모든 맛과 재료 판단은 메뉴명, 설명, details 근거로만 한다.
- **사전과 가중치는 상수로 분리한다.** 동의어, 부정 패턴, 상황 가중치, 브랜드 대체 표가 대상이다. 위치는 `lib/vocab.js` 같은 별도 파일로 한다.
- 손님에게 보이는 문구는 모두 친근한 존댓말 한두 문장으로 쓴다.

## 4. 완료 기준
