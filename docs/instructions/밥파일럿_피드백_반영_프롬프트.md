# 밥파일럿 — 현직자 피드백 반영 작업 프롬프트 (Seoul_AI_HACKATHON 저장소용)

너는 이 저장소(배달앱 '당겨요' 데모 안의 "메뉴 추천" 기능 = 밥파일럿)의 개발을 맡은 엔지니어다. 2026 서울AI디지털배움터 청년AI해커톤에서 받은 현직자 피드백을 코드에 반영하는 것이 이번 작업이다. 본선은 6시간 안에 끝까지 동작하는 데모가 목표이므로 **데모 안정성 > 화면 개선 > 지표 > 확장** 순으로 처리한다.

## 저장소 지도 (작업 전에 직접 확인할 것)

| 위치 | 역할 |
|---|---|
| `api/recommend.js` | Vercel 함수. Supabase RPC `seoul_recommendation_snapshot`으로 가게·메뉴를 받아 2분 캐시 → `createEngine` → `handle(state, action, ai)` |
| `lib/ai.js` | Gemini 호출(`createGemini`) + AI ①②③ 프롬프트(`PARSE_SYSTEM`, `QUESTION_SYSTEM`, `JUDGE_SYSTEM`)와 JSON 스키마가 한 파일에 섞여 있음 |
| `lib/engine.js` (약 1,100줄) | 규칙 파서(`ruleParse`), 기준가·총액(`ctx`), 필터(`filterStores`), 점수(`priceScore`, `ratingScore`), 키워드 판단(`keywordJudge`), 질문(`question`), 결과(`results`), 양보안(`concessions`, `zero`), 노출 횟수(`exposure`, 서버 메모리), 진입점 `handle` |
| `dist/recommend.html` | 추천 화면(칩, 남은 가게 수, 카드 렌더링, `/api/recommend` 호출) |
| `dist/index.html`, `customer.js`, `cart.js`, `merchant.*` | 당겨요 주문자 홈·장바구니·사장님 라운지 (추천 외 데모) |
| `supabase/migrations/` | `recommendation_catalog.stores/menus` 테이블과 snapshot 함수, 주문 데모용 테이블 |
| `stores_excel`, `menus_excel` | 원본 CSV (가게 242곳, 메뉴 1,181개) |
| `test/recommend.test.js` | 엔진 테스트 14개. 실행: `node --test test/recommend.test.js` (`node --test test/`로는 실패하니 파일을 지정할 것) |

## 0. 먼저 할 일 (코드 수정 전)

1. 위 지도가 맞는지 확인하고, 아래 작업 목록 각 항목이 **이미 구현됨 / 일부 구현됨 / 미구현** 중 무엇인지 표로 정리한다.
2. 변경 계획(파일별로 무엇을 바꿀지)을 먼저 보여주고, 확인을 받은 뒤 구현한다.
3. 작업은 항목별로 작은 커밋으로 나눈다. 커밋 메시지에 항목 번호를 넣는다 (예: `[P0-1] LLM 호출 어댑터 분리`).
4. 매 커밋 전에 `node --test test/recommend.test.js`가 모두 통과해야 한다. 새 기능에는 같은 파일 형식으로 테스트를 추가한다.

## 1. 바꾸면 안 되는 원칙

- 판단·계산(필터, 점수, 순위, 총액, 가격 비교)은 코드, 말 이해·질문·설명은 AI.
- AI가 돌려준 store_id·menu_id는 코드가 검증하고 없는 id는 버린다 (`results`, `question`에 이미 있음 — 유지).
- AI ③(`judge`)에는 가격을 넘기지 않는다.
- 광고·할인·브랜드·주문 수는 점수에 0. 점수 = 조건 일치 50 + 가격 30 + 별점 20.
- 대화는 저장하지 않는다. 로그인 없음.
- `GEMINI_API_KEY` 등 비밀 키는 Vercel 환경 변수에만. `dist/supabase-config.js`의 publishable 키는 브라우저용이라 공개돼도 되지만, 그 키로 접근 가능한 범위는 RLS로 막혀 있어야 한다.

## 2. 작업 목록

### P0 — 데모 안정성 (반드시)

**P0-1. LLM 호출과 프롬프트·응답 검증 분리** (`lib/ai.js`, `api/recommend.js`)
피드백: 핵심 모델이 정해지지 않았음. 모델이 바뀌어도 같은 JSON을 받도록 분리할 것.
- 현재 `lib/ai.js` 하나에 프롬프트·스키마·Gemini 호출·파싱이 다 들어 있다. 다음처럼 나눈다.
  - `lib/prompts.js`: `PARSE_SYSTEM`, `QUESTION_SYSTEM`, `JUDGE_SYSTEM`과 각 스키마
  - `lib/llm/gemini.js` (+ 필요하면 `lib/llm/openai.js`): `complete({ system, payload, schema }) → 문자열`만 구현
  - `lib/llm/index.js`: `createLLM()`이 `LLM_PROVIDER`(기본 gemini)로 어댑터를 고르고, 지금 `createGemini()`와 같은 모양(`used`, `parse`, `question`, `judge`)을 돌려준다
  - 응답 검증 공통 함수: JSON 파싱 → 스키마 필수 필드·enum 검사 → 실패 시 **1번 재요청** → 그래도 실패하면 throw (엔진이 이미 규칙 기반으로 폴백함)
- 지금 `callJson`은 한 번 실패하면 `failed = true`가 되어 그 요청 안의 나머지 AI 호출을 모두 건너뛴다. 설계(1번 재요청)와 다르니 고친다. 단, 타임아웃이나 키 없음처럼 재시도해도 소용없는 실패는 바로 폴백한다.
- `api/recommend.js`의 `provider: ai.used ? "gemini" : "rules"`는 실제 쓰인 provider 이름이 나오게 바꾼다.
- `README.md`에 환경 변수(`LLM_PROVIDER`, `GEMINI_API_KEY`, `GEMINI_MODEL`, 추가한 provider 키)를 정리한다.

**P0-2. AI 입력 상한을 상수로** (`lib/engine.js`의 `question`, `results`)
피드백: 선택지 질문은 남은 가게 메뉴 설명을 모두 읽어 후보가 많으면 토큰·지연이 커짐. 숫자를 정할 것.
- 현재 하드코딩된 값: `question`은 가게 16곳 × 메뉴 8개 × 설명 100자, `results`는 후보 8곳 × 메뉴 10개 × 설명 100자.
- 파일 상단(또는 `lib/config.js`)에 상수로 모으고 아래 값으로 줄인다 [제안, 벤치마크 후 조정]:
  - `AI2_MAX_STORES = 12`, `AI2_MAX_MENUS_PER_STORE = 3`, `AI2_DESC_MAX_CHARS = 60`
  - `AI3_MAX_CANDIDATES = 8`, `AI3_MAX_MENUS_PER_STORE = 5`, `AI3_DESC_MAX_CHARS = 100`
- `AI2_MAX_STORES`를 넘을 때 어떤 가게를 보낼지는 `results`의 후보 상한과 같은 사전 점수(가격+별점, 동점은 노출 적은 순)로 고른다. 지금처럼 `left.slice(0, 16)` 앞부분만 자르지 않는다.

**P0-3. 응답 시간 측정과 대기 표시** (`api/recommend.js`, `lib/llm/*`, `dist/recommend.html`)
피드백: 한 턴에 AI 최대 2번 + 질문 최대 3번이라 대기가 쌓임.
- 서버: 카탈로그 로드, AI ①·②·③ 호출, 전체 처리 시간을 측정해 응답에 `timing` 필드로 넣는다. 화면 표시는 `?debug=1`일 때만.
- 현재 Gemini 타임아웃 6.5초 × 최대 2회 + Supabase 6.5초 + 재요청을 더하면 `vercel.json`의 `maxDuration: 30`에 가까워질 수 있다. 턴 전체 예산(예: 12초)을 두고, 남은 시간이 부족하면 재요청 없이 규칙 기반으로 폴백한다.
- `scripts/bench.js`: 설계서의 시연 질문 5개를 실제 Gemini로 연속 실행해 단계별 평균·최대 시간을 출력한다. 목표: 턴당 5초 안팎.
- `dist/recommend.html`의 `fetch('/api/recommend', ...)` 대기 중에 단계 문구를 보여준다 ("조건 정리 중 → 가게 찾는 중 → 추천 이유 정리 중", 서버 단계를 모르면 시간으로 순서대로 바꿔도 됨). 대기 중에는 입력과 버튼의 중복 전송을 막는다.

**P0-4. 데이터·스키마를 설계와 맞추기** (`supabase/migrations/`, `stores_excel`, `lib/engine.js`)
피드백: 시연 데이터 규모를 정해 미리 넣어 둘 것 / 리뷰가 적은 가게의 별점 기준을 정할 것.
현재 확인된 차이:
- `stores_excel`은 앞 42줄은 쉼표, 나머지 200줄은 탭으로 구분돼 섞여 있다. 한 형식(쉼표 CSV)으로 정리하고 확장자를 `.csv`로 바꾼다.
- CSV에는 `review_count`, `is_open`, `exposure_count`가 있지만 `recommendation_catalog.stores`와 snapshot 함수에는 없다. 그 결과:
  - **영업중 필터가 동작하지 않는다** (`filterStores`에 영업 여부 조건이 없음).
  - **보정 별점이 구현돼 있지 않다.** `ratingScore`가 리뷰 수 없이 `s.rating ?? 동네 평균`만 쓴다. 리뷰 3개짜리 5.0 가게(예: S39)가 리뷰 500개짜리 4.6 가게보다 높게 나온다.
  - 최소주문금액이 없어 엔진에서 `minOrder: 0`으로 고정돼 있다.
- 또 테이블의 `rating`이 `not null`인데 CSV에는 별점이 빈 신규 가게(리뷰 0개)가 많다. DB에 실제로 어떻게 들어갔는지 확인한다. 0으로 들어갔다면 `rating >= 3.5` 필터에 걸려 **신규 가게가 전부 빠지고 있는 것**이므로 가장 먼저 고친다.
- 할 일:
  1. 새 마이그레이션: `stores`에 `review_count integer not null default 0`, `is_open boolean not null default true`, `min_order integer not null default 0` 추가, `rating`은 null 허용. `menus`에 `is_main boolean`(null 허용) 추가. snapshot 함수에 이 필드들을 포함한다.
  2. CSV를 다시 넣는 시드 스크립트 `scripts/seed-catalog.js`(또는 SQL)를 만든다. 별점이 비면 null.
  3. 엔진: `filterStores`에 `is_open` 조건, `minOrder`는 DB 값, `mains`는 `is_main`이 있으면 우선 사용하고 없을 때만 지금의 중앙값 50% 규칙을 쓴다.
  4. `ratingScore`를 설계대로 바꾼다: 보정 별점 = (리뷰 수 × 별점 + 10 × 동네 평균) ÷ (리뷰 수 + 10). 리뷰 0개면 동네 평균(중립). 별점 문턱 3.5는 **보정 전 별점이 있는 가게에만** 적용하고 신규 가게는 통과시킨다.
  5. 테스트 추가: 리뷰 1개 5.0 가게가 1등이 되지 않음 / 리뷰 0개 가게가 필터에서 빠지지 않음 / 영업 안 하는 가게는 빠짐.

### P1 — 화면 개선 (`dist/recommend.html`, `lib/engine.js`의 `chips`, `concessions`, `zero`)

**P1-1. 시작 화면: 동네 → 말하기 순서로 묶기**
- 동네 선택, 예시 문장, 하단 입력창이 떨어져 있음 → "① 배달받을 동네 → ② 먹고 싶은 음식 말하기"가 한 덩어리로 보이게.
- 예시는 짧은 칩으로 바꾸고 눌러서 조합되게: `혼자 먹어요` `둘이 먹어요` `2만 원 이하` `가성비` `프랜차이즈 말고` `매운 거`. 칩을 누르면 입력창에 이어 붙는다.
- 음성 입력은 이번에 구현하지 않으면 입력창 옆에 이름이 붙은 큰 마이크 버튼("말로 하기") 자리만 비워 둔다.

**P1-2. 결과 카드: 세 가게의 차이가 보이게**
- 메뉴명과 총액을 가장 크게. 지금 `.head`에 가게 이름과 별점, `.total`이 아래에 있다 → 메뉴명·총액을 위로.
- 메뉴 사진(데이터에 있으면), 구성·양·맛 차이를 세 카드 모두 같은 위치에.
- `.quote`의 "사장님 설명" 라벨을 "사장님 메뉴 소개"로 바꾸고 인용은 짧게(예: 40자).
- 세 카드에 똑같이 붙는 ✓(`c.checks`)는 결과 위에 한 번만("세 곳 모두: 영업중 · 프랜차이즈 아님"), 카드에는 그 가게만 다른 항목만 남긴다.
- `JUDGE_SYSTEM`에 "reason에는 quote의 표현을 반복하지 말고, 손님 조건과 어떻게 맞는지만 한 줄로" 규칙을 추가한다.

**P1-3. 0곳 화면: 바뀌는 조건을 숫자로** (`concessions`)
- 지금 "2,000원만 더 쓰면 2곳 있어요" → 버튼 아래에 "예산 25,000원 → 27,000원"을 함께 표시. 다른 양보안도 같은 형식("순살 → 상관없음", "프랜차이즈 제외 → 포함", "동네 보통 가격 → +10%").
- 양보안 객체에 `change: { from, to }` 필드를 추가해 화면이 그대로 그리게 한다.

**P1-4. 결과 화면에서 조건만 수정**
- 결과 화면의 칩(`chips(state)`)을 눌러 예산·음식 조건을 바로 고치면 설계 v3의 재계산 표대로 다시 계산한다(처음부터 X). 지금 칩을 누를 수 있는지 확인하고, 안 되면 예산 칩 → [2만][2.5만][3만][직접 입력], 음식 칩 → 업종 버튼을 띄운다.

### P1 — 공정한 노출 지표 (기획 피드백 4번)

**P1-5. 노출 횟수 저장 위치 옮기기 + 지표 집계**
- 지금 `exposure`는 서버 메모리라서 서버리스 인스턴스마다 초기화된다(코드 주석에도 적혀 있음). Supabase에 `recommendation_catalog.impressions`(날짜, store_id, 횟수) 같은 테이블을 만들어 옮긴다. 읽기는 snapshot에 포함하고, 쓰기는 RPC 하나로.
- 추천 결과 단위 익명 집계 테이블(날짜, 동, 업종, 가격 모드, TOP3 store_id, 각 가게의 프랜차이즈 여부)을 만든다. 대화 내용·입력 문장은 저장하지 않는다.
- 지표: ① TOP3 중 비프랜차이즈 비율 ② 가게별 노출 분포(상위 20% 가게의 노출 비중) ③ 한 번도 노출되지 않은 가게 수. 시연용 `dist/metrics.html` 한 장 또는 `scripts/metrics.js`.

**P1-6. 손님 만족도**
- 결과 아래에 "이 추천 괜찮았어요? 👍 / 👎" 버튼. P1-5의 결과 집계 행에 붙여서만 저장.

### P2 — 여유가 있으면

**P2-1. 메뉴 설명 유불리 (기획 피드백 3번)**
- `JUDGE_SYSTEM`에 이미 "설명 없으면 이름으로 최소 '일부'", "근거 없는 자랑은 '일부'까지" 규칙이 있다. `keywordJudge`(AI 실패 시)도 같은 규칙인지 확인하고 테스트를 추가한다. CSV에는 설명이 빈 메뉴가 122개 있으니 이 데이터로 확인한다.
- 사장님 메뉴 설명 도우미(사장님 라운지 `dist/merchant.html`의 메뉴 편집에서 재료·양·맛을 고르면 설명 문장을 만들어 주는 기능)는 화면 목업 수준으로만 넣거나 기획서에 남긴다.

**P2-2. 기존 방식 vs 밥파일럿 비교**
- 같은 요청을 ① "기존 방식"(필터 없이 Gemini에 가게 목록을 주고 추천받기, 또는 별점순 정렬) ② 밥파일럿 엔진으로 처리해 나란히 보여주는 `dist/compare.html` 또는 `scripts/compare.js`. 편의점 섞임, 총액 누락, 프랜차이즈 쏠림, 영업 안 하는 가게 포함 같은 차이가 드러나게.

**P2-3. AI 호출 합치기 실험**
- AI ①(parse)과 ③(judge)을 한 번의 호출로 합칠 수 있는지 플래그(`MERGE_AI_CALLS`, 기본 off)로 실험하고 P0-3 벤치마크로 시간·결과를 비교해 보고만 한다.
